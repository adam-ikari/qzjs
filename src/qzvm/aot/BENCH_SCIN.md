### 五个运行时的定位

| 对照 | 结论 |
|---|---|
| vs 解释器（同引擎 QuickJS） | **9-46×**。AOT 相对自身解释器的收益，最干净的 AOT 价值度量。 |
| vs CPython | **9-65×**（几何 29×）。CPython 无 JIT，循环体每轮走字节码派发 + float 装箱，故普遍慢于 QuickJS 解释器 1.2-2.3×。 |
| vs V8 | **0.35-4.0×，几何 1.30×**。数值密集且无数组分配时 AOT 常胜（nbody 4.0×、mcpi 2.8×）；嵌套数组/整数型循环上 V8 靠边界检查消除 + 标量替换胜出（matmul 0.57×、张量积 0.35×）。 |
| vs C（gcc -O2） | **0.06-1.03×，几何 0.46×**，即 AOT 落后原生约 2.2×（中位）。mcpi/mcpiNum **已追平**（1.01-1.03×）、nbodyNum 0.98× 基本持平 —— 数据依赖强、不可重排的标量 f64 循环里 wasm 数值路径**已是原生水平**。 |

### vs C 的差距：已排除 SIMD，确认是优化器能力

最初怀疑「C 侧自动向量化」。**实测否决**：`gcc -O2 -fno-tree-vectorize` 与 `-O2` 各负载差异 ≤5%（matmul 0.71 vs 0.76、sieve 0.27 vs 0.26、张量积 1.52 vs 1.56），这些循环对本机 SSE/AVX **不可向量化**（`(i%7)-3` 这类整数取模、以及 `a*b` 累加的浮点结合顺序依赖）。

真实差距来源（按实测贡献）：

1. **C 的常量折叠（已在本基准里堵掉）**。`bench_scin.c` 各函数入口有 `KEEP_IMM` 汇编屏障。不加时 gcc 会把 `matmul(120)` 整个循环算成编译期常量 —— `nm` 里连 `matmul`/`matmulNum` 符号都不剩，`objdump main` 只剩一条 `mulsd`。堵掉后 matmul 从 0.76→1.14ms（matmulNum 1.35→1.46ms）。**AOT 侧 `n` 恒为运行期实参，不吃这个便宜，故必须给 C 加屏障才公平。**
2. **循环展开 + 强度削减**。sieve 0.06×（17×）是最极端项：C 把内层 `for (j=i*i; j<=limit; j+=i) c[j]=0` 展开成多路写、并把 `j<=limit` 的比较提到寄存器；AOT 是逐元素 `f64Load`/`f64Store` + 显式 `i32TruncF64S`（数组下标从 f64 截断）。
3. **数组下标的 f64→i32 截断**。`a[i]` 在 TS 里 `i` 是 double，emitter 每次下标访问发一条 `i32TruncF64S`（emitter.js:2327-2331）。C 侧循环变量本就是 `long`，零转换。这是 matmul（0.18×）/张量积（0.24×）差距的主要成分。
4. **无 SIMD128 发射**。当前 emitter 不发 wasm SIMD，故即便循环可向量化也没有对应收益。但**实测这些负载都不可向量化**，所以此项不是当前差距的来源 —— 它只是「若将来换成可向量化的负载（如连续点积、图像卷积）」时才成为杠杆。

## 关键结论

**1. 模式判定已不是分水岭——数组不再是阻断项。** `funcMode()` 现在允许 `number[]`
局部数组、零参箭头内联，故 11 个负载全部走 `num`（f64 直算 + i32 展平数组）。
历史上「同一 N 体算法 426ms(tagged 数组) vs 1.77ms(num 标量)、差 241 倍」已消失：
两种写法现在同在 num 路径，差 7.6 倍（1.97 vs 0.26，因标量版每次重建而非复用数组）。

**2. 仍留在 `tagged` 的是对象/字符串动态 I/O**，见 `bench_mix.js`：

| 负载 | AOT ms | 解释器 ms | V8 ms | AOT/解释器 | AOT/V8 |
|---|---:|---:|---:|---:|---:|
| numWork（纯数值循环） | 341.0 | 10392.6 | 757.4 | **30.5×** | 2.22× |
| objWork（每轮对象分配） | 2.67 | 7.70 | 0.10 | **2.88×** | 1/26.7× |
| strWork（字符串拼接，AOT wasm） | 26.7 | 27.0 | 5.66 | 1.01× | 1/4.7× |

`objWork` 的剩余差距来自分配而非数值运算：同一负载去掉对象分配、只留等价算术，
200k 轮从 5ms 降到 1ms。静态 bump 堆无 GC、无逃逸分析，V8 能把 `{id,sq}` 完全标量替换掉——
这是结构性差距。

已在分配热路径上拿掉一部分：`_emitFillUndef` 原用运行时 loop 逐 8 字节写 `undefined` 句柄
（比较/分支/指针自增），改为按编译期常量 size 展开成定长 `i64.store`（≤8 槽）。
实测 `objReal` 300k 轮 **5ms → 3ms**（每轮 17ns → 10ns，**分配路径提速 40%**），
wasm 3613B → 3006B（-17%）。bench 的 objWork 参数只有 30000 轮，被固定开销主导，
看不出这项收益——它的真实量级要用 30 万轮以上的循环测。

**循环级 arena 回滚**（已解决原先的硬天花板）：bump 堆只增不减、无回收，每实例 40 字节
（由全局字段表 `__cls,id,sq,tag` 决定，非实际用到的字段数），原先**约 40 万次（419427）分配
即耗尽 16 MiB arena** 并崩溃。现由 `_loopArenaFree` 做逃逸判定：循环体内「对象字面量初始化」
的 let/const 变量若只以 `x.field` / `x[..]` 出现（从不被传递/返回/存入容器/闭包捕获），
且循环体内无 `return`/`throw`/闭包，则判定对象生命周期不越过当前迭代 → 循环入口存 bump、
每轮末尾复位（`_arenaLoopEnter` / `_arenaLoopLeave`）。`for` / `while` / `do-while` 三种
形态统一走该路径。分配量 O(迭代数) → **O(1)**。实测 `objLoop` **300 万轮 26ms**、1000 万轮
91ms（此前 40 万轮即崩）；`while`/`do-while` 等价写法 200 万轮各 17 / 22ms。
`while` 的 `continue` 直接跳回条件、会跳过该轮复位——只少回收、不影响正确性。
不安全场景（存数组、赋外部变量、中途 return、闭包捕获）判定为 false 时**完全不复位**，
9 条 `loop-alloc-*` 语料与 V8 逐值一致。

**函数级 arena 回滚**：循环回滚看不到「循环体本身不分配、但每轮调用的被调函数内分配」的形态
——`for (…) t = t + mk(i)` 里 `mk` 每次造一个临时对象、只读字段、返回标量，对象无人持有，
41.9 万次调用后 arena 耗尽。由 `_fnArenaFree` 判定后在**每个 return 前**把 bump 复位到
函数入口（`_fnArenaSlot`）。判据必须能**证明返回值不指向 arena**，否则复位会让返回值悬空
（静默内存 corruption，比崩溃更糟）：① 返回类型标注是 `number`/`boolean`/`void`/`undefined`；
② 函数体内确有分配（对象字面量 / 数组字面量 / `new`）；③ 无 `try`/`throw`/闭包；④ 分配物局部
只以 `x.field` / `x[..]` 出现（`return p` 这种整体逃逸会被拒绝）；⑤ `new C(…)` 还要求构造体
对本实例只做 `this.field` 读写（`return this`、存容器、传参、被闭包捕获都算泄漏 → 拒绝，
否则复位让那个外部引用悬空）。实测 `manyCalls` **200 万轮 20ms、1000 万轮 106ms**（此前
41.9 万轮即崩）；返回对象的 `manyRetObj` 照旧耗尽 arena —— 正确拒绝。
9 条 `fn-alloc-*` 语料覆盖对象字面量 / 数组 / `new` 的接受与拒绝（返回 any、返回对象、
构造体泄漏 this）。
剩余限制：仍无真正的回收器；被跨调用持有或存入容器/全局的对象无法回收，长驻服务需要
region / 引用计数。
另有既存性能缺陷（与回滚无关）：`new C()` 每次实例化约 **3.4µs**，而对象字面量约 10ns
（差 300 倍），`loopBox` 10 万轮 348ms —— 回归前实测同为 349ms，属独立待查项。

`strWork` 现已走 AOT wasm（不再 `--interp` 回退）。历史上它因每轮 `s = s + i` 都调
`qz.str_dup` 复制整串而呈 **Θ(n²)**——200000 次直接 bump arena 溢出崩溃（实测 N>2291 即崩）。
根因是逃逸分析 `_strAccSetOf` 把 `return s` 判为逃逸，导致累加器从未被识别。
放宽为「函数末尾纯返回也可原地追加」后走 `qzs_append` 的 bump-顶分支，复杂度回到 O(n)：
200000 次从**崩溃**变为 26.7ms（解释器 27.0ms）。真正的别名风险（`const a = s` 后再累加）、
自拼接、循环内提前 return、多 return 分支仍回退复制，边界语料见 `audit_corpus4.js` 的 `str-acc-*`。

## 本次优化（tagged 路径指令数）

三项 NaN-box 判定原先逐标签线性比较，改为一次无符号区间测试（标签恰好连续）：

| 判定 | 原指令数 | 现指令数 | 区间 |
|---|---:|---:|---|
| `_emitIsHandle` | 24（7 路 eq + or，含 BigInt 特例） | 5 | `[0x7FF8_0000_0000_0001, 0x7FFF_FFFF_FFFF_FFFF]` |
| `_emitIsBig` | 11（hi 比较 + 低32 非零 + and） | 5 | `[0x7FF8_0000_0000_0001, 0x7FF8_FFFF_FFFF_FFFF]` |

唯一坑：`0x7FF8|0` 是 canonical NaN（`box(NaN)` 的位型），必须当数值——恰好卡在区间下界前一位，
故下界取 `…0001`。负数位型（≥`0x8000…`）因无符号减法越界而天然排除，无需额外分支。

效果：`mix.wasm` 35471 → 30959 B（-12.7%），`scin.wasm` 11453 → 10533 B（-8.0%）。
`objWork` 对 V8 从 58.4× 慢改善到 19.3-27× 慢（运行间波动大，V8 侧常被标量替换到 <0.1ms）。

## 另修：全 `--interp` 产物编译崩溃

`build.js build <src> <prefix> --interp <全部函数>` 曾抛 `Error: call 未定义: qzs_ckmem`：
`emitNumArrHelpers` 无条件发射，但它依赖的 `qzs_ckmem` / `qzs_memcpy` 定义在
`emitStringHelpers` 里，而后者只在 `anyTagged` 分支调用。修复：抽出 `emitMemHelpers`
（两个基础 helper 的归属），并让 `emitNumArrHelpers` 与 `emitStringHelpers` 都在
`anyTagged` 分支内、按 `emitMemHelpers → emitStringHelpers → emitNumArrHelpers` 顺序发射。
